# tasksAreUs — Architecture

## System Overview

- **Backend**: Python / FastAPI / PostgreSQL; Docker for dev
- **Frontend (web)**: React 19 + Vite + TypeScript + Tailwind CSS; runs in the browser
- **Frontend (mobile)**: React Native + Expo SDK 54 (managed workflow) + TypeScript + NativeWind v4; runs on iOS and Android
- **Multi-tenant**: every table includes `user_id`; full data isolation per user

## Identity

**Phase 2 (current):** Firebase Auth is the primary identity mechanism end-to-end. The backend initializes the Firebase Admin SDK using `FIREBASE_SERVICE_ACCOUNT_JSON` (fail-fast if missing). Both the web frontend and mobile app use the Firebase JS/RN SDK initialised from `VITE_FIREBASE_*` / `EXPO_PUBLIC_FIREBASE_*` env vars respectively. On first load, `AuthContext` silently calls `signInAnonymously()` — zero-friction UX identical to Phase 1. Named sign-in (Google or magic link) is offered in Settings. Authenticated requests from `client.ts` (web) and `apiFetch` (mobile) send `Authorization: Bearer <firebase_id_token>` obtained via `auth.currentUser?.getIdToken()`.

**Backend auth:** `get_current_user()` in `dependencies.py` verifies the Bearer token with the Firebase Admin SDK, looks up the user by `firebase_uid`, and auto-creates a new user row on first sign-in. Bearer token is the only accepted auth path. The same `/api/v1` endpoints serve both web and mobile clients.

## Key Implementation Patterns

**Schema management**: `Base.metadata.create_all()` on startup. No migrations file — all schema changes run as idempotent `ALTER TABLE` / `CREATE INDEX IF NOT EXISTS` / `DROP INDEX IF EXISTS` statements in `main.py`'s lifespan block. The `boards` table is created by `create_all()` on first run; the partial unique index on `(user_id) WHERE is_default = true AND is_deleted = false` is created separately via raw SQL because SQLAlchemy `UniqueConstraint` does not support partial indexes.

**Board scoping**: All resources (tasks, labels) belong to exactly one board. `board_service.resolve_board_id(db, user_id, board_id?)` is the single entry point for board resolution in all routers — it validates ownership when `board_id` is supplied and calls `ensure_board_seeded()` when it is omitted, returning the user's default board and lazily creating "General tasks" + seeding 9 default labels for brand-new users. New boards created by users via `POST /boards` start empty (no label seeding). `MAX_BOARDS_PER_USER = 10` is enforced by `board_service.create_board()`.

**Active board (web frontend)**: `BoardContext` tracks the user's currently selected board in React state. On mount, `BoardProvider` calls `GET /boards` and sets `activeBoard` to the board with `is_default === true`. Active board is never persisted to `localStorage` — every app open resets to the default board (unless restored from a URL `?board=` param — see below). `setActiveBoard` calls `FilterContext.clearLabels()` when the board actually changes (labels from one board are not valid in another). Direct API calls in pages (`ReportsPage`, `SettingsPage`) and the `useTasks` hook read `activeBoard.id` and pass it as `board_id`. `useLabels` reads `activeBoard.id` by default but accepts an optional override (see below). Every `BoardContext` mutation (create, rename, set-default, set-color, delete) awaits `fetchBoards()` to refresh the full boards list — no local-state patching. `setColorBoard(id, color)` calls `updateBoard(id, { color })` then `fetchBoards()` so the board list (and swatches) reflect the new color immediately. **PR #41**: `BoardSwitcher.tsx` (the always-visible sidebar/header dropdown) was removed; board switching now happens via `BoardTabs.tsx`, rendered only under the Tasks page's All view. `TasksPage` also programmatically restores `activeBoard` from a `?board=` URL param once `boards` has loaded, and both `TasksPage` (All view) and `TaskDetailPage` (edit mode) can now reflect or select a board other than `activeBoard` — Today/Tomorrow/Focused views and the task's own board are cross-board and don't necessarily match `activeBoard`.

**Board-scoped label fetching override (PR #41)**: `useLabels(boardIdOverride?: string)` fetches labels for `activeBoard.id` by default, but when a caller passes a defined `boardIdOverride` it fetches for that board instead and no longer waits on `activeBoard`/`BoardContext` to resolve. `TaskDetailPage` uses this to scope the label picker to the task's own `board_id` (edit) or the create target board (new) rather than whatever board happens to be globally active — necessary because Today/Tomorrow/Focused are cross-board views. `TaskForm`'s in-form board `<select>` (the board-move picker) reports every selection change back to its parent via an `onBoardIdChange` prop; `TaskDetailPage` feeds this into its own `liveBoardId` state, which takes priority over the task's/target's own board when computing `labelsBoardId` for `useLabels()` — so the visible label list re-scopes live as the user changes the board within the form, and `TaskForm` separately clears any already-selected label IDs when the in-form board actually changes (not on its initial resolution). This closes a gap previously flagged here (as of PR #41) where the form's label list did not track its own in-form board selection; fixed by commits predating PR #45.

**Label seeding (board-scoped)**: `label_service.seed_board_labels(db, board_id, user_id)` seeds the 5 LABEL_SEED entries (type labels only; mode labels removed in PR #51) into a specific board. It is called only during initial board creation (via `ensure_board_seeded` in `board_service`). New boards created by users are NOT seeded. The sentinel is "this board has 0 labels" — checked per-board, not per-user.

**API proxy**: Vite dev server proxies `/api` to `http://localhost:8000`, so the frontend makes same-origin requests and CORS is not an issue in development.

**AI beliefs** (`generate_beliefs`): single JSON-mode Claude call; response parsed for `label_suggestions` (label_id + rationale) and `time_estimate_minutes`.

**High-priority tasks**: `is_high_priority` is only valid when the task's effective date (earliest of `must_do_by` / `target_date`) is overdue, today, tomorrow, day_after_tomorrow, or monday (as of PR #54). Auto-reset to `false` on any update that moves the date outside that window. The daily cap is user-configurable via `user_settings.high_priority_daily_limit` (default 3, min 1); `_get_high_priority_limit()` in `task_service.py` reads it on each create/update, falling back to 3. HTTP 422 is raised when the cap is exceeded. The cap does not apply within the Overdue column — tasks retain their existing priority there, but the cap re-engages when a task is dragged to Today, Tomorrow, Day After Tomorrow, or Monday. When a column exceeds the limit, the column header shows an amber ⚠ N/M high badge (warning only — no retroactive enforcement). Across all views (Focused, Today, Tomorrow, All, Day View on web and mobile), high-priority tasks appear first within their board/column/section, sorted by `is_high_priority DESC` before `updated_at` (as of PR #47).

**Null-clearing on update**: `PUT /tasks/{task_id}` uses Pydantic `model_fields_set` to distinguish "field not provided" from "field explicitly set to null". `clear_must_do_by` and `clear_target_date` flags are passed to `update_task` to allow clearing date fields to null. The `TaskForm` component sends an explicit `null` when a previously-set date is cleared via the × button, ensuring the backend actually clears the field.

**Overdue column**: Tasks whose effective date is strictly in the past are assigned to the `overdue` column bucket (`ColumnKey = 'overdue' | 'today' | 'tomorrow' | 'day_after_tomorrow' | 'monday' | 'upcoming' | 'nodate'`). The Overdue column uses a red accent style and is **hidden entirely when it contains no tasks**. Dropping tasks *into* the Overdue column is blocked; tasks can only drag *out* to other columns. `getDropDate('overdue')` returns `null` (same as `nodate`). `isHighPriorityEligible` returns `true` for `overdue` so existing high-priority flags are preserved.

**Upcoming column (read-only drop target)**: The Upcoming column (and Upcoming section on mobile) is **blocked as a drop target** — dragging a task over it shows no highlight, and dropping is a no-op. The column placeholder shows "Read-only" on web (mobile: the section header does not highlight during drag). This matches the Overdue blocking. Tasks naturally fall into Upcoming by having a `target_date` beyond tomorrow+1; that date is not settable by drag.

**Day After Tomorrow column**: `getColumn()` detects tasks whose effective date falls on today+2 and assigns them to the `day_after_tomorrow` bucket. `getDropDate('day_after_tomorrow')` returns today+2. `isHighPriorityEligible` returns `true` for `day_after_tomorrow` — tasks can be marked high-priority in this column (added in PR #54). The column has collapsible high-priority and always-visible normal-priority zones with session-only collapse state.

**Monday column (PR #54)**: When today is Friday, the All view renders an additional `monday` column after Day After Tomorrow (computed via `new Date(tomorrow).setDate(tomorrow.getDate() + 1)` when `new Date().getDay() === 5`). The Monday column has high-priority and normal-priority task zones with collapsible headers, matching Today/Tomorrow/Day After Tomorrow. `getColumn()` returns `'monday'` when today is Friday and a task's effective date equals Monday; `getDropDate('monday')` returns the Monday date. `isHighPriorityEligible` returns `true` for `'monday'` — tasks can be marked high-priority. The column disappears immediately after Friday ends locally (as `isFriday()` re-evaluates to `false` on page render); this is a UI-only feature — tasks already assigned to Monday remain on Monday in the backend but become unreachable from the kanban until the next Friday.

**Firebase Auth flow (Phase 2 frontend):** `AuthContext` mounts a single `onAuthStateChanged` listener. When `firebaseUser === null` and no deliberate sign-out is recorded in `sessionStorage` (`auth_signed_out`), it calls `signInAnonymously()` automatically — the user never sees a login screen. Deliberate sign-out sets `sessionStorage.auth_signed_out = '1'`, which prevents the auto-sign-in on the next listener fire; `LoginPage` is shown instead. Magic-link callbacks are handled on page load: if `localStorage.emailForSignIn` is present (same device), sign-in completes immediately; otherwise `EmailConfirmationPage` (an inline component in `App.tsx`) prompts the user for their email before completing the cross-device sign-in.

**Firebase Auth flow (mobile):** Mirrors the web pattern with React Native–specific adaptations. `AsyncStorage` replaces `localStorage`/`sessionStorage`. Auth persistence uses `getReactNativePersistence(AsyncStorage)` so the Firebase session survives app restarts. The deliberate-sign-out flag is a module-level variable (resets on force-quit — correct behaviour for a mobile app). Magic-link deep links are received via `expo-linking`: `Linking.getInitialURL()` handles cold-start links; `Linking.addEventListener('url', ...)` handles links while the app is open. Google Sign-In uses `expo-auth-session/providers/google` with separate web/iOS/Android client IDs from `EXPO_PUBLIC_GOOGLE_*_CLIENT_ID` env vars. In Expo Go, the Google OAuth redirect is `exp://[local-ip]:8081` and must be added to Google Cloud Console. Magic link deep linking only works fully in standalone builds; Expo Go cannot redirect back from the browser.

**Mobile form navigation (pageSheet Modal):** `TaskFormScreen` is not registered in the navigator; it is presented as a React Native `<Modal animationType="slide" presentationStyle="pageSheet">` owned by `TasksScreen`. This avoids a nested stack navigator and keeps the form decoupled — `TasksScreen` tracks `formVisible: boolean` and `editingTaskId: string | undefined` in local state. `onSave` and `onCancel` callbacks close the modal and trigger a silent re-fetch. When opening in create mode, `TasksScreen` passes `initialLabelIds={[...selectedLabelIds]}` to pre-select the currently active label filters in the form; in edit mode, `initialLabelIds` is `undefined` so the form always reflects the task's own labels. This pattern is the approved approach for full-screen forms in the mobile app.

**Mobile API error handling (ApiError):** `mobile/src/api/client.ts` exports an `ApiError` class (extends `Error`) with a readonly `status: number` property equal to the HTTP response status code. All `apiFetch` errors are thrown as `ApiError`. Callers use `instanceof ApiError` to branch on specific HTTP statuses (e.g. `err.status === 422` to catch the high-priority daily limit and display a user-friendly `Alert` without treating it as a generic failure). This pattern replaces the old practice of parsing error strings.

**Mobile drag-drop (TasksScreen):** Long-pressing a pending task for 500ms activates a `react-native-gesture-handler` Pan gesture via `GestureDetector`. A `TaskGhost` component floats at the finger position using `react-native-reanimated` shared values (`ghostY`, `ghostVisible`) updated in worklets to avoid JS-thread jank. The JS thread receives `runOnJS` callbacks (`onDragActivate`, `onDragMove`, `onDragEnd`) for target hit-testing and state updates. Section header Y positions are recorded via `onLayout`; hit-testing maps the finger's scroll-adjusted Y coordinate to the nearest section. On drop, only `target_date` is updated via `PUT /tasks/{id}` — matching web behaviour (`must_do_by` is never modified by drag). Dropping onto Overdue or Upcoming is rejected — `updateDragTarget` maps both to `null` (no highlight); `performDrop` returns early for both. The HP daily limit (fetched from `GET /settings` on every focus) is enforced client-side for today/tomorrow drops of already-HP tasks. Auto-scroll uses a 16ms `setInterval` that drives `getScrollResponder().scrollTo()` (an internal RN API used because `SectionList.scrollToLocation` does not support arbitrary Y offsets).

**Active board (mobile):** `BoardContext` tracks the user's currently selected board in React state. On mount, `BoardProvider` calls `GET /boards` and sets `activeBoard` to the default board (or the first board if no default exists). Active board is never persisted to `AsyncStorage` — every app open resets to the default board. `setActiveBoard` is called directly from the board switcher in `TasksScreen` (visible only in All view); no label clearing happens in `BoardContext` itself. Instead, each screen uses `useEffect([activeBoard?.id])` to react to board changes: `TasksScreen` clears label filters and search query (show-completed toggle removed in PR #46). Every `BoardContext` mutation (create, rename, set-default, set-color, delete) awaits `fetchBoards()` to refresh the full boards list — no local-state patching. `setColorBoard(id, color)` calls `updateBoard(id, { color })` then `fetchBoards()` so the board list (and swatches in SettingsScreen) reflect the new color immediately.

It is consumed by both `TaskRow` (All view, `layout="inline"`) and `FocusedTaskCard` (Focused/Today/Tomorrow views, `layout="stacked"`) — extracted to close a parity gap where mobile's `FocusedTaskCard` had lacked Links/Complete/Delete buttons. It renders title, priority badge, dates, labels, links, and an Edit/Complete/Delete action row. Differences from web: mobile's `priorityBadge` is always `'static'` (no toggle affordance — both call sites use `'static'` with no `onTogglePriority`); both mobile call sites use `dateDisplay: {mode:'effective', effectiveDate}` (no `'split'` variant on mobile); and the action row gates Edit/Complete/Delete on `task.state === 'pending'` as inherited from TaskRow's pre-existing gate, which is inert in mobile's new UI since the "Show completed" toggle has been removed and only pending tasks are ever displayed (PR #46).

**Mobile 4-way view system (PR #46):** `TasksScreen` reworked to replace the old 2-way Detailed/Focused toggle and "Show completed" toggle with a 4-way pill toggle (Focused, Today, Tomorrow, All) — default Focused. Focused renders `<FocusedView />` (GET /focused-view/tasks); Today/Tomorrow render `<DayView referenceDate={...} />` (GET /day-view/tasks for that single date); All renders the grouped-list SectionList with drag-drop, search, and label filters. Completing a task now removes it from view entirely — there is no remaining "Show completed" path in mobile's UI (unlike before). `DayView` (new component, PR #46) fetches GET /day-view/tasks for a caller-supplied `referenceDate` and delegates rendering to the shared `BoardGroupedTasks` component. Both `FocusedView` and `DayView` can be cross-board and show tasks from multiple boards grouped by board color.

**No shared module between web and mobile:** TypeScript types (`types/index.ts`) and pure utility functions (`taskDateUtils`, `taskFilters`, `taskPriority`, `taskLinks`) are duplicated from `frontend/src/` into `mobile/src/`. This is intentional — avoids monorepo complexity at the cost of keeping them in sync manually. `taskGrouping.ts` is mobile-only (no web equivalent) because the web app uses a kanban column layout rather than a grouped list. `isFormHighPriorityEligible` is also mobile-only — the web app's `TaskForm` derives eligibility from the selected column context rather than inspecting raw date strings. `chatUtils.ts` was removed in PR #46 when the Chat feature was deleted from mobile.

**Task links:** A task may have up to `MAX_TASK_LINKS = 3` links, each `{id, url, description}`. `url` must start with `http://` or `https://` (rejects `javascript:`, `data:`, `mailto:`, etc. — both client-side via `isValidLinkUrl()` before submit and server-side via the `TaskLink` Pydantic `field_validator`); `description` must be non-empty after trim. `PUT /tasks/{id}` uses full-replace semantics for `links`, matching `label_ids`: omitting the field leaves existing links unchanged, any list (including `[]`) fully replaces the set. Both `TaskForm` (web) and `TaskFormScreen` (mobile) always send `links` on save so an empty array actually clears existing links. On the `/sync` push path, `SyncChanges.tasks` are raw dicts that bypass `TaskCreate`/`TaskUpdate` Pydantic validation entirely, so `sync.py`'s `_validate_sync_links()` re-validates each link independently via `TaskLink.model_validate()`; unlike the REST endpoints (where one invalid link fails the whole request with 422), an item-level failure during sync just drops that one link rather than discarding the whole array, and the result is capped at `MAX_TASK_LINKS`. Web renders read-only links (on task cards) as `<a target="_blank" rel="noopener noreferrer">` (native tooltip on hover shows the URL); mobile renders them as tappable chips that call `Linking.openURL()` after re-validating the scheme via `TaskCardBody.tsx`'s local `openTaskLink()` helper. `schemas.py` also defines an all-or-nothing `validate_task_links()` helper that is no longer called from application code (sync.py moved to per-item validation) — it is exercised only by `tests/unit/test_schemas.py`.

**Link editing UX in the form (PR #52, web + mobile):** `TaskForm`/`TaskFormScreen`'s links editor no longer has an explicit "+ Add link" button. A `useEffect` on the `links` state calls `withReadyLinkRow(links, newLinkId)` (`utils/taskLinks.ts`) after every change, which appends one blank row whenever the list doesn't already end in a single blank row and is under `MAX_TASK_LINKS` — so the user always has a ready-to-fill row without an extra step — and dedupes any extra blank rows down to the first (preserving its id) if a filled row is cleared back to blank. Each row whose `url` currently passes `isValidLinkUrl()` also shows an open-in-new-tab affordance next to the URL input: an `<a target="_blank" rel="noopener noreferrer">` icon on web, a `Linking.openURL()` `TouchableOpacity` on mobile.

**Day View:** `GET /day-view/tasks?reference_date=YYYY-MM-DD&overdue=false` (`reference_date` required — no server-side default, unlike `GET /focused-view/tasks`; `overdue` optional, defaults to `false`, added PR #55) returns all pending tasks — any priority, across all boards — whose `must_do_by` or `target_date` falls on that single date (`overdue=false`, the default) or falls strictly before it (`overdue=true`), using the same OR-across-both-fields filter shape either way (`==` vs `<`). It ignores the user's Focused View config entirely (no `board_selection`/`day_range` concept). `focused_view_service._query_board_grouped_tasks()` is the shared query/grouping helper behind both `get_focused_tasks()` and `get_day_view_tasks()` — as of PR #55 it takes already-resolved, already-ordered `Board` objects and a caller-built SQLAlchemy `date_filter` clause (previously a fixed date window; each caller now builds its own `or_(...)` clause before calling in), and optionally filters to `is_high_priority == True`. Tasks within each board group are sorted by `is_high_priority DESC` (high-priority first), then `updated_at` DESC (as of PR #47). Response reuses the existing `FocusedViewTasksOut` shape. Added in PR #40 as backend groundwork for the web/mobile Today/Tomorrow views (later PRs in the same epic); extended in PR #55 to also back the Overdue view (see "Overdue view" above) — no new router or endpoint was added for Overdue.

**Move task between boards:** `TaskUpdate.board_id` (`Optional[str] = None`) lets a task move to a different board via `PUT /tasks/{id}` or `/sync` push. `task_service.update_task()` validates the destination board via `board_service.get_board_or_404()` (404 if not owned or soft-deleted) and unconditionally clears the task's labels when the board actually changes — regardless of whether the same request also sends `label_ids` — because labels are board-scoped and a label from the old board has no meaning on the new one. If `label_ids` is also sent in the same request, it is resolved against the *new* `board_id` (labels are re-added after the move). Omitting `board_id`, or sending the task's current `board_id`, is a no-op that leaves labels untouched. The `/sync` push path writes `server_task.board_id` directly from the client payload without calling `get_board_or_404()` — it does not validate that the destination board exists, is owned by the caller, or is not soft-deleted before assigning it. Added in PR #40.

**Web Tasks page four-view redesign (PR #41):** `TasksPage` replaces the old Detailed/Focused + Show done/pending toggles with four views — **Focused** (default), **Today**, **Tomorrow**, **All** — selected by a pill toggle and encoded in the URL as `?view=`. Focused renders `<FocusedView />` (`GET /focused-view/tasks`); Today/Tomorrow render `<DayView referenceDate={...} />` (`GET /day-view/tasks`, backend from PR #40) for today's/tomorrow's date respectively; All renders the pre-existing 6-column kanban board, gated to `viewMode === 'all'` alongside its loading/error banners, label filter chips, and search box. `BoardGroupedTasks` is a shared renderer (colored board header + card grid) used by both `FocusedView` and `DayView`, extracted in this PR to avoid duplicating the per-board grouping/coloring logic. `BoardTabs` (board switcher pills) renders only under All and writes the selected board into `?board=`; a `TasksPage` effect restores `activeBoard` from `?board=` once boards finish loading async. Completing a task now makes it disappear from the web UI entirely — there is no remaining "Show done" view (mobile is unaffected and still has a Show completed toggle). The FAB always opens `/tasks/new?board=<id>` — the active board under All, otherwise the user's default board.

**Chat feature removal (web PR #41, mobile PR #46, backend PR #50):** Web's `ChatPage.tsx`, its `/chat` route and nav item, and `api/conversations.ts` were deleted in PR #41. Mobile's `ChatScreen.tsx`, `api/conversations.ts`, and related utilities (`chatUtils.ts`, `chatUtils.test.ts`) were deleted in PR #46. PR #50 completed the removal end-to-end on the backend: the `conversations`/`messages` routers, SQLAlchemy models, Pydantic schemas, and `ai_service.handle_conversation_message()`/`_CONV_TOOLS`/`_format_task_line()` were deleted, and the `conversations`/`messages` tables were dropped via a `DROP TABLE IF EXISTS` startup migration in `main.py` (no backup — the feature had no users). The orphaned `user_settings.starter_questions` column (only ever fed the removed chat screen's quick-start chips) was also dropped end-to-end (backend model/schema/router/sync, web `SettingsPage.tsx`, mobile `SettingsScreen.tsx`). No conversational backend surface remains; a future chat rebuild would need to reintroduce this layer from scratch.

**Board picker on TaskForm (PR #41):** `TaskForm` accepts `boards: Board[]` and `defaultBoardId?: string` props and renders a board `<select>` (shown whenever boards exist) on both create and edit. Selecting a different board than the task's current one (edit mode) shows an inline warning that the move will clear the task's labels, matching `task_service.update_task()`'s board-move behavior. See "Board-scoped label fetching override" above — the label list shown in the form now re-scopes live as the in-form board selection changes (fixed by commits predating PR #45).

**Mobile label badge colors (NativeWind):** Dynamic Tailwind class interpolation is unsafe in NativeWind v4. `TasksScreen.tsx` uses inline `style` props (`backgroundColor`, `color`) driven by lookup objects (`LABEL_BG`, `LABEL_TEXT`) keyed by label category, rather than dynamic class strings. This is the approved pattern for per-category colors in mobile components.

**Sticky Tasks-page view state (PR #42):** `ViewContext` (`ViewProvider`/`useView()`) holds the web Tasks page's `viewMode` in React state, wrapped around `BrowserRouter` alongside `BoardProvider` in `App.tsx` — it is session-only (not persisted to `localStorage`), mirroring how `BoardContext`'s `activeBoard` already behaves. It exists because `Layout.tsx`'s nav links point at bare paths (`/`, `/reports`, `/settings`) with no query string, so navigating away from Tasks and back would otherwise reset `viewMode` to whatever the (now-empty) `?view=` URL param implies. `TasksPage` reads/writes `viewMode` through this context; `setView(v)` (the view-toggle handler) updates both the context and the URL together, and a `useEffect` restores `viewMode` from `?view=` only when the URL disagrees with the context (hard reload or a shared link) so the two don't fight during normal in-app navigation. `TaskDetailPage`'s save/complete/delete handlers already used `navigate(-1)` (PR #41), which independently preserves the full `?view=&board=` query string for that specific back-navigation; `ViewContext` covers the remaining paths (Reports, Settings) where the query string is dropped.

**Shared task quick-edit component (PR #42):** `TaskQuickEdit` is a small extracted component (title input + mode/type label toggle buttons + Save/Cancel) that replaces what used to be edit state and logic duplicated inside `TaskCard` alone. It is now used by both `TaskCard` (the All view's kanban card) and `FocusedTaskCard` (Focused/Today/Tomorrow), giving all four Tasks-page views the same quick inline-edit affordance. It takes an optional `labels?: Label[]` prop: `TaskCard` passes the label list it already has for the active (single) board; `FocusedTaskCard` omits it, since Focused/Today/Tomorrow group tasks from multiple boards in one screen, and `TaskQuickEdit` instead fetches board-scoped labels itself via `listLabels(undefined, task.board_id)` in a cancellation-guarded effect — independent of the `useLabels` hook and its `boardIdOverride` (PR #41). Both `BoardGroupedTasks` and its `FocusedView`/`DayView` callers now thread an `onRefresh` callback (the view's own task-fetch function) down to each `FocusedTaskCard` so a quick-edit save triggers a re-fetch, matching how `TaskCard` already called `onRefresh` from its parent kanban column.

**Shared task card body (PR #45):** `TaskCardBody` extracts the read-only render (badges, title, dates, labels, links, Edit/Complete/Delete action row) previously hand-duplicated across `TaskCard` (All view) and `FocusedTaskCard` (Focused/Today/Tomorrow) — the duplication is what let `FocusedTaskCard` silently fall behind `TaskCard` on Links/Complete/Delete. Real visual/behavioral differences between the two cards are captured as props rather than forked markup: a `dateDisplay` discriminated union (`'split'` vs `'effective'`), a `layout` union (`'inline'` vs `'stacked'`, driving both flex structure and title styling), a `priorityBadge` union (`'toggle'` vs `'static'`), and a `renderLabels` render-prop so each caller keeps its own label sort order and badge styling. `handleComplete`/`handleDelete` are not part of this extraction — each of `TaskCard.tsx` and `FocusedTaskCard.tsx` still implements its own (near-identical) API-call handlers and passes them down as `onComplete`/`onDelete` props.

**Board-neutral Settings labels (web PR #42, mobile PR #46):** Both web's `SettingsPage` and mobile's `SettingsScreen` now handle board-scoped labels independently of the globally active board. A local `labelsBoardId` state (initialised to `activeBoard?.id ?? boards[0].id`, and re-resolved if the currently-selected board disappears) decides which board's labels are fetched/created/shown; a dropdown (web `<select>`, mobile picker) — rendered only when `boards.length > 1` — lets the user switch it independently of the app's globally active board. This means opening Settings to edit a different board's labels does not change which board is active in Tasks/Reports elsewhere in the app. High Priority Daily Limit and Starter Questions are board-neutral (global per-user settings); Reports remains scoped to the single globally active board — making it board-neutral is explicitly out of scope since `GET /reports/completions` only supports one `board_id` at a time.

**TaskForm mount stability across board switches (PR #48):** `TaskDetailPage` previously gated `<TaskForm>`'s render entirely on `pageLoading = loading || labelsLoading`. Since `TaskForm` reports every in-form board selection change up to the parent via `onBoardIdChange` (see "Board-scoped label fetching override" above) and the parent re-scopes `useLabels()` to the new board, picking a different board mid-edit set `labelsLoading = true` and briefly unmounted `<TaskForm>` while the new board's labels loaded, then remounted it. Because `TaskForm` is an uncontrolled component (title/notes/dates/board/labels live in local `useState`, seeded once from `initialValues`), the remount silently reset the in-progress board selection — and any other unsaved edits — back to the last-saved task. The fix tracks, via `mountedForIdRef`, whether the form has already completed its first full load (task + labels) for the current task `id` — reset alongside the existing `id`-keyed fetch effect. Only that initial load is gated on `labelsLoading`; once mounted, a later board-switch-triggered labels reload leaves `<TaskForm>` mounted, instead passing `labelsLoading` down as a prop so `TaskForm` can show an inline "Loading labels…" placeholder in the Labels section. A second ref, `lastLabelsBoardIdRef`, guards the one render where `labelsBoardId` first resolves but `useLabels`'s `loading` flag hasn't caught up yet. The same PR also fixed `handleSubmit` never calling `setSaving(false)` on the edit-success path (only the `catch` branch reset it), which had left "Save Changes" stuck on "Saving…" after every successful edit.

**Board collapse/expand (PR #53, web + mobile):** Focused, Today, and Tomorrow (not All) support per-board collapse/expand plus a per-view "Collapse all / Expand all" toggle. State is session-only — never sent to the backend or persisted to `localStorage`/`AsyncStorage` — scoped independently per view (`'focused' | 'today' | 'tomorrow'`), and survives in-app navigation away and back but resets to fully-expanded on a hard page reload / app restart. The mechanism intentionally differs by platform for the same requirement: **web** uses a new `BoardCollapseContext` (`BoardCollapseProvider`/`useBoardCollapse()`) wrapped around `BrowserRouter` in `App.tsx`, because `TasksPage` (and everything under it) fully unmounts on navigation to Task Detail/Reports/Settings — the same reason `ViewContext` (PR #42) exists. **Mobile** instead lifts the collapse state into `TasksScreen`'s own `useState` (`collapsedBoards: Record<BoardViewKey, Set<string>>`, threaded down as props through `FocusedView`/`DayView` into `BoardGroupedTasks`) because React Navigation's bottom-tab navigator keeps `TasksScreen` mounted across tab switches and task editing happens in an in-screen `<Modal>`, not a separate route — no context is needed, mirroring how `expandedSections` (the All view's kanban section collapse, unrelated state) already lives in the same component. On both platforms, a board's id left in a collapsed `Set` after that board is deleted/renamed is inert for the rest of the session (never cleaned up) rather than actively pruned, and neither platform resets collapse state on an identity switch (anon → authenticated) since board ids are UUIDs scoped to the owning account.

**Overdue view (PR #55, web + mobile):** A fifth, conditionally-rendered top-level Tasks-page view — Overdue — sits to the left of Focused in the pill toggle, shown only when the caller has at least one overdue task, and becomes the default view (instead of Focused) on page load/first tab focus when overdue tasks exist. "Overdue" = a pending task whose effective date (earliest of `must_do_by`/`target_date` when both are set, otherwise whichever is non-null) is strictly before today — the same definition already used by the All view's kanban Overdue column, but this is a distinct, separate view (the kanban column is unaffected and unrelated). No new backend endpoint: `GET /day-view/tasks` (see "Day View" below) gained an `overdue: bool = Query(default=False)` param, reusing the same board-grouped, any-priority, single-comparison query shape Today/Tomorrow already use, just switching `==` to `<` on both date fields. On both platforms, a mount-time (web) / every-tab-focus (mobile) check calls `getDayViewTasks(today, true)`; a one-shot ref (`appliedDefaultRef` web / `appliedDefaultViewRef` mobile), set only inside the resolved `.then()` continuation — never synchronously at effect entry — applies the Overdue default exactly once per session/first-focus, avoiding a bug class where a premature synchronous ref-set would consume the one-shot guard before the async check resolves and silently prevent the default from ever applying (caught by Sneezy's plan review before implementation). Both platforms also gate first paint behind this same check settling (`overdueChecked` web / `initialGateResolved` mobile, both flipped via `.finally()` so a network failure can't hang the gate) so the app doesn't flash the Focused view — and issue a wasted `/focused-view/tasks` fetch — before the default-view decision is known. Accepted, documented tradeoffs (not fixed in this PR): the tab-visibility check and the mounted Overdue view's own fetch both hit `GET /day-view/tasks?...&overdue=true` independently, so the "Overdue is default" path issues two near-identical requests — once at load on web, and on every tab refocus on mobile (worse, since mobile's `useFocusEffect` re-runs the check on every return to the Tasks tab); and there is no live re-check mid-session, so a task becoming overdue after the initial check (midnight rollover, backdating) won't surface the pill until the next full reload/app relaunch.

**Search across all views (PR #56, web only):** The task search box (title + notes, client-side substring match) previously filtered only the All view's kanban board. `TasksPage` now passes `searchQuery` down into all five views: `filterTasks` (All view, unchanged behavior, now built on the shared `matchesSearch` predicate in `utils/taskFilters.ts`) and the new `filterBoards(boards, searchQuery)` (Overdue/Focused/Today/Tomorrow, applied inside `BoardGroupedTasks`). `filterBoards` filters each board's task list independently and drops boards left with zero matches; when the raw board list was non-empty but the filtered result is empty, `BoardGroupedTasks` renders a "No tasks match this search" empty state in place of its normal output, suppressing the "Collapse all"/"Expand all" toggle so it never points at nothing. This is a web-only change — mobile's `TasksScreen` search remains scoped to the All view's filter panel, unchanged by this PR. (Search box positioning was subsequently moved by PR #57 — see below.)

**All-view UX polish (PR #57, web only):** Nine small polish items on the web Tasks page, all frontend-only (no backend/API/data-model changes). (1) Sticky high-priority collapse: the All view's per-column high-priority-zone collapse state moved out of `TasksPage`'s local `useState` into a new `ColumnPriorityCollapseContext` (mirroring `BoardCollapseContext`'s already-established "mount above `BrowserRouter`" pattern, keyed only by `ColumnKey` since it's All-view-only) — collapse state now survives navigating to a task's edit page and back. (2) Each priority-eligible column's "High Priority" zone header shows a live count, "High Priority (n)". (3)/(4) The filter-chip row's redundant "Tags" label (`CATEGORY_DISPLAY_NAMES`) was removed and "Clear filters" is right-aligned under the chips. (5) The search `<input>` (introduced All-view-only, extended to all views in PR #56) now renders as the topmost element on the page, above the title/view-toggle Header block and unconditionally (not gated on the `overdueChecked` first-paint check) — a bigger reorder than "move to the top" might suggest at a glance, since it now sits above "Tasks Are Us - `{view}`" itself, not just above `BoardTabs`. (6) `TaskCard`'s label container always renders (no longer `null` for zero-label tasks) with a `min-h-[2.75rem]` (2 chip rows) floor, so switching boards no longer changes card/column height depending on how many labels each board's tasks carry; `FocusedTaskCard`'s equivalent pattern in Focused/Today/Tomorrow was intentionally left out of scope, flagged as a known follow-up. (7)/(8) `taskDateUtils.formatDateWithDay()` switched from full to abbreviated weekday names (`'long'` → `'short'`), and `TasksPage`'s `COLUMNS` memo now carries `{ title, dateLabel? }` per entry instead of one pre-concatenated title string, so column headers render the date label on its own line below the column name. (9) `TaskQuickEdit`'s label buttons are now alphabetized by `label.value`, matching the sort already used by the filter-chip row.

For auth, soft deletes, recurring task rules, beliefs storage, sync protocol, and cost tracking see `DATA_MODEL_AND_API.MD`.
