# tasksAreUs — Architecture

## System Overview

- **Backend**: Python / FastAPI / PostgreSQL; Docker for dev
- **Frontend (web)**: React 19 + Vite + TypeScript + Tailwind CSS; runs in the browser
- **Frontend (mobile)**: React Native + Expo SDK 54 (managed workflow) + TypeScript + NativeWind v4; runs on iOS and Android
- **Multi-tenant**: every table includes `user_id`; full data isolation per user

## Identity

**Phase 2 (current):** Firebase Auth is the primary identity mechanism end-to-end. The backend initializes the Firebase Admin SDK using `FIREBASE_SERVICE_ACCOUNT_JSON` (fail-fast if missing). Both the web frontend and mobile app use the Firebase JS/RN SDK initialised from `VITE_FIREBASE_*` / `EXPO_PUBLIC_FIREBASE_*` env vars respectively. On first load, `AuthContext` silently calls `signInAnonymously()` — zero-friction UX identical to Phase 1. Named sign-in (Google or magic link) is offered in Settings. Authenticated requests from `client.ts` (web) and `apiFetch` (mobile) send `Authorization: Bearer <firebase_id_token>` obtained via `auth.currentUser?.getIdToken()`.

**Backend auth:** `get_current_user()` in `dependencies.py` verifies the Bearer token with the Firebase Admin SDK, looks up the user by `firebase_uid`, and auto-creates a new user row on first sign-in. Bearer token is the only accepted auth path. The same `/api/v1` endpoints serve both web and mobile clients.

## Key Implementation Patterns

**Schema management**: `Base.metadata.create_all()` on startup. No migrations file — all schema changes run as idempotent `ALTER TABLE` / `CREATE INDEX IF NOT EXISTS` / `DROP INDEX IF EXISTS` statements in `main.py`'s lifespan block. The `boards` table is created by `create_all()` on first run; the partial unique index on `(user_id) WHERE is_default = true AND is_deleted = false` is created separately via raw SQL because SQLAlchemy `UniqueConstraint` does not support partial indexes.

**Board scoping**: All resources (tasks, labels) belong to exactly one board. `board_service.resolve_board_id(db, user_id, board_id?)` is the single entry point for board resolution in all routers — it validates ownership when `board_id` is supplied and calls `ensure_board_seeded()` when it is omitted, returning the user's default board and lazily creating "General tasks" + seeding 9 default labels for brand-new users. New boards created by users via `POST /boards` start empty (no label seeding). `MAX_BOARDS_PER_USER = 10` is enforced by `board_service.create_board()`.

**Active board (web frontend)**: `BoardContext` tracks the user's currently selected board in React state. On mount, `BoardProvider` calls `GET /boards` and sets `activeBoard` to the board with `is_default === true` (server-derived from custom order as of PR #62 — see "Board order and order-driven default" below). Active board is never persisted to `localStorage` — every app open resets to the default board (unless restored from a URL `?board=` param — see below). Through PR #70/#71, `setActiveBoard` called `FilterContext.clearLabels()` when the board actually changed, clearing the global tag-filter selection on every switch; as of PR #75 it no longer does — `FilterContext`'s per-board selection map (see "Tag filter modes and per-board persistence" below) keeps each board's tags isolated automatically, so switching tabs now restores whatever was last selected for that board instead of starting clean. Direct API calls in `SettingsPage` and the `useTasks` hook read `activeBoard.id` and pass it as `board_id`. `ArchivePage` no longer reads `activeBoard` directly as of PR #63 — its own `<ArchiveBoardTabs>` carries independent local board-selection state, defaulting to `all_boards=true` rather than the globally active board (see "Archive board filtering" below). `useLabels` reads `activeBoard.id` by default but accepts an optional override (see below). Every `BoardContext` mutation (create, rename, reorder, set-color, delete) awaits `fetchBoards()` to refresh the full boards list — no local-state patching. `setColorBoard(id, color)` calls `updateBoard(id, { color })` then `fetchBoards()` so the board list (and swatches) reflect the new color immediately. **PR #41**: `BoardSwitcher.tsx` (the always-visible sidebar/header dropdown) was removed; board switching now happens via `BoardTabs.tsx`, rendered only under the Tasks page's All view. `TasksPage` also programmatically restores `activeBoard` from a `?board=` URL param once `boards` has loaded, and both `TasksPage` (All view) and `TaskDetailPage` (edit mode) can now reflect or select a board other than `activeBoard` — Today/Tomorrow/Focused views and the task's own board are cross-board and don't necessarily match `activeBoard`.

**Board-scoped label fetching override (PR #41)**: `useLabels(boardIdOverride?: string)` fetches labels for `activeBoard.id` by default, but when a caller passes a defined `boardIdOverride` it fetches for that board instead and no longer waits on `activeBoard`/`BoardContext` to resolve. `TaskDetailPage` uses this to scope the label picker to the task's own `board_id` (edit) or the create target board (new) rather than whatever board happens to be globally active — necessary because Today/Tomorrow/Focused are cross-board views. `TaskForm`'s in-form board `<select>` (the board-move picker) reports every selection change back to its parent via an `onBoardIdChange` prop; `TaskDetailPage` feeds this into its own `liveBoardId` state, which takes priority over the task's/target's own board when computing `labelsBoardId` for `useLabels()` — so the visible label list re-scopes live as the user changes the board within the form, and `TaskForm` separately clears any already-selected label IDs when the in-form board actually changes (not on its initial resolution). This closes a gap previously flagged here (as of PR #41) where the form's label list did not track its own in-form board selection; fixed by commits predating PR #45.

**Label seeding (board-scoped)**: `label_service.seed_board_labels(db, board_id, user_id)` seeds the 5 LABEL_SEED entries (type labels only; mode labels removed in PR #51) into a specific board. It is called only during initial board creation (via `ensure_board_seeded` in `board_service`). New boards created by users are NOT seeded. The sentinel is "this board has 0 labels" — checked per-board, not per-user.

**API proxy**: Vite dev server proxies `/api` to `http://localhost:8000`, so the frontend makes same-origin requests and CORS is not an issue in development.

**High-priority tasks (PR #72 — tri-state `priority`):** `priority` (`high` / `medium` / `normal`, default `normal`) is the tier field; the legacy `is_high_priority` boolean is kept as a mirrored/derived column (`task.is_high_priority = (task.priority == "high")` on every write) for pre-OTA mobile clients — see Table `tasks` in `DATA_MODEL_AND_API.MD`. `high`/`medium` are only valid when the task's effective date (earliest of `must_do_by` / `target_date`) is overdue, today, tomorrow, day_after_tomorrow, or monday (web board eligibility since PR #54; backend `_is_hp_eligible_date()` in `task_service.py` — unchanged eligibility window, now shared by both tiers instead of gating a single boolean). Auto-reset to `normal` on any create/update that resolves to `high`/`medium` but whose effective date falls outside that window; `normal` itself has no date restriction. The daily cap applies only to `high` (`medium`/`normal` are uncapped — explicit product decision, no Medium limit planned) and is user-configurable via `user_settings.high_priority_daily_limit` (default 3, min 1); `_get_high_priority_limit()` in `task_service.py` reads it on each create/update, falling back to 3. HTTP 422 is raised when the cap is exceeded. **Correction:** `_is_hp_eligible_date()` treats every past date as eligible, so the cap actually re-engages on any update that resolves to an explicit High intent even for an already-overdue task (e.g. a plain re-save from the mobile Edit Task screen or web's `TaskForm`) — this replaces a previously-stated "the cap does not apply within the Overdue column" claim here, which was inaccurate; see "Cap re-engagement on overdue tasks" in `DATA_MODEL_AND_API.MD`. When a column exceeds the High limit, the column header shows an amber ⚠ N/M high badge (warning only — no retroactive enforcement). Across all views (Focused, Today, Tomorrow, All, Day View on web and mobile), tasks are ranked by tier before the tiebreak: web's All-view kanban and mobile's non-Overdue sections use the 3-way `TIER_RANK` map (`high: 0, medium: 1, normal: 2`; `TasksPage.tsx`/`taskGrouping.ts`, PR #73) then `sort_order ASC` (changed PR #61, was `updated_at DESC` as of PR #47); the Focused/Today/Tomorrow backend query (`focused_view_service._query_board_grouped_tasks()`) only distinguishes `high` from everything else (`Task.priority == "high"` DESC, then `sort_order` ASC — PR #72) since Medium never surfaces there (High-only, per product decision); web's Overdue column also ranks by the full 3-way `TIER_RANK` (generalized from a 2-way `is_high_priority` split in PR #73), tiebreaking on effective-date ASC; mobile's Overdue section deliberately keeps the old 2-way high/not-high split with `updated_at DESC` (see "Drag-to-reorder within a column" below for the web/mobile divergence); and `target_date ASC` (not a priority split) is unchanged for the read-only Upcoming column/section.

**Null-clearing on update**: `PUT /tasks/{task_id}` uses Pydantic `model_fields_set` to distinguish "field not provided" from "field explicitly set to null". `clear_must_do_by` and `clear_target_date` flags are passed to `update_task` to allow clearing date fields to null. The `TaskForm` component sends an explicit `null` when a previously-set date is cleared via the × button, ensuring the backend actually clears the field.

**Overdue column**: Tasks whose effective date is strictly in the past are assigned to the `overdue` column bucket (`ColumnKey = 'overdue' | 'today' | 'tomorrow' | 'day_after_tomorrow' | 'monday' | 'upcoming' | 'nodate'`). The Overdue column uses a red accent style and is **hidden entirely when it contains no tasks**. Dropping tasks *into* the Overdue column is blocked; tasks can only drag *out* to other columns. `getDropDate('overdue')` returns `null` (same as `nodate`). **Correction:** `isPriorityEligible` (renamed from `isHighPriorityEligible` — web in PR #73, mobile in PR #74; both now tier-aware, gating High and Medium alike) returns `false` for `'overdue'`, not `true` as previously stated here — that has been the case since well before PR #72/#73 and is unaffected by this migration. Overdue's own 3-tier (High/Medium/Normal) zoned card layout, using the same `renderTierZone()` machinery as the eligible columns below, is driven by a separate `isOverdueCol` check in `TasksPage.tsx` (`isPriorityColumn = isPriorityEligible(col.key) || isOverdueCol`); the per-task priority toggle button is gated on `isPriorityEligible(col.key)` alone, so it does not render for tasks in Overdue — existing priority tiers there are preserved simply because nothing in the Overdue UI can change them.

**Upcoming column (read-only drop target)**: The Upcoming column (and Upcoming section on mobile) is **blocked as a drop target** — dragging a task over it shows no highlight, and dropping is a no-op. The column placeholder shows "Read-only" on web (mobile: the section header does not highlight during drag). This matches the Overdue blocking. Tasks naturally fall into Upcoming by having a `target_date` beyond tomorrow+1; that date is not settable by drag.

**Day After Tomorrow column**: `getColumn()` detects tasks whose effective date falls on today+2 and assigns them to the `day_after_tomorrow` bucket. `getDropDate('day_after_tomorrow')` returns today+2. `isPriorityEligible` (renamed from `isHighPriorityEligible` — PR #73) returns `true` for `day_after_tomorrow` — tasks can be marked High or Medium in this column (Medium added PR #73; High since PR #54). As of PR #73 the column renders three independently-collapsible zones — High, Medium, Normal (`TIER_META`/`renderTierZone()` in `TasksPage.tsx`, keyed via `ColumnPriorityCollapseContext`'s `` `${ColumnKey}:${PriorityTier}` `` collapse key) — replacing the previous 2-zone (collapsible-high, always-visible-normal) layout; collapse state remains session-only.

**Monday column (PR #54)**: When today is Friday, the All view renders an additional `monday` column after Day After Tomorrow (computed via `new Date(tomorrow).setDate(tomorrow.getDate() + 1)` when `new Date().getDay() === 5`). As of PR #73, the Monday column has three independently-collapsible zones — High, Medium, Normal — with the same `renderTierZone()` collapsible-header machinery as Today/Tomorrow/Day After Tomorrow (previously a 2-zone collapsible-high/always-visible-normal layout). `getColumn()` returns `'monday'` when today is Friday and a task's effective date equals Monday; `getDropDate('monday')` returns the Monday date. `isPriorityEligible` (renamed from `isHighPriorityEligible` — PR #73) returns `true` for `'monday'` — tasks can be marked High or Medium. The column disappears immediately after Friday ends locally (as `isFriday()` re-evaluates to `false` on page render); this is a UI-only feature — tasks already assigned to Monday remain on Monday in the backend but become unreachable from the kanban until the next Friday.

**Drag-and-drop date semantics**: When a task is dragged to a dated column, `TasksPage` always updates `target_date` only — `must_do_by` is never modified by drag-and-drop. This preserves any hard deadline the user set explicitly. When dragging to the `nodate` column, only `target_date` is cleared (set to `null`); `must_do_by` is left untouched. `getEffectiveDateField()` exists in `taskDateUtils.ts` but is not used in the drag-drop path. As of PR #61, every drop (including a same-column, same-zone reorder) also computes and sends an explicit `sort_order` — see "Drag-to-reorder within a column" below.

**Drag-to-reorder within a column (PR #61, web only; tier handling generalized in PR #73):** `tasks.sort_order` (`DOUBLE PRECISION NOT NULL`) is a client-computed fractional index — the server never renumbers rows. `_sort_order_default()` (`models.py`) returns `datetime.now(timezone.utc).timestamp()`; it's both `Task.sort_order`'s Python-side column default (so every new task lands after all older ones) and the value used any time a task is auto-reset to "bottom of list" (real time only moves forward, so a fresh default always sorts after any previously-assigned value in the same list). Existing rows were backfilled from `created_at` in the startup migration (`main.py`). On the web All-view kanban, every `TaskCard` now tracks drag-over position via a new `onCardDragOver` prop (fires on `dragover`, computing `'above'`/`'below'` from the pointer's Y position against the card's bounding-rect midpoint) and renders an optional `dropIndicator` border; `TasksPage` stores the live `dragOverTaskId`/`dragOverEdge` in state. On drop, `handleDrop` derives the destination zone's existing tasks via `splitByPriority(columnTasks[columnKey])` (the already-imported `taskPriority.ts` helper — not a variable inherited from the render loop; returns `{high, medium, normal}` as of PR #73, was `{high, normal}`) and calls `computeInsertSortOrder()` (`utils/taskOrder.ts`) to compute the new task's position, sending it as `sort_order` alongside the existing `target_date`/`priority` fields on every drop — including a same-column, same-zone reorder. The drop payload field is `priority` (`PriorityTier`) as of PR #73 — was `is_high_priority`; web no longer sends the legacy field on its own writes (see PLAN-feat-priority-tiers.md). Server-side, `task_service.update_task()`'s `sort_order` param wins outright when supplied (even alongside a simultaneous date/board change); when omitted, the server auto-resets `sort_order` to "bottom of list" whenever the task's effective date or `board_id` actually changed (a Task Form date edit, a board move, or a mobile date-drag all trigger this even though none of them pass `sort_order`), and otherwise leaves it untouched. `routers/sync.py`'s client-wins branch duplicates this same reset rule by hand (importing `task_service._effective_date()`) since that router bypasses `task_service` entirely — this matters for offline mobile drags queued and later pushed via `/sync`. Ordering by column (web, `TasksPage.tsx`): `overdue` sorts by the 3-way `TIER_RANK` map (`high: 0, medium: 1, normal: 2`; generalized from a 2-way `is_high_priority` DESC split in PR #73), then effective-date ASC — still no manual reorder, no `sort_order` involvement; `upcoming` sorts by `target_date` ASC (nulls last) — also not manually orderable; every other column (Today, Tomorrow, Day After Tomorrow, Monday, No Date) sorts by the same `TIER_RANK` map, then `sort_order` ASC. The same `sort_order`-ASC tiebreak was also adopted by `focused_view_service._query_board_grouped_tasks()` (`order_by_sort_order: bool` param, PR #61) for `get_focused_tasks()` and `get_day_view_tasks(overdue=False)` — i.e. the Focused/Today/Tomorrow views, which have no reorder UI of their own but now reflect the same manual order set on the All-view kanban — while `get_day_view_tasks(overdue=True)` (the Overdue view) keeps the pre-existing `updated_at DESC` tiebreak; that backend query only ever distinguishes `high` from everything else (`Task.priority == "high"` DESC, PR #72), never the full 3-way rank, since Medium never surfaces in Focused/Day View. **Web/mobile divergence on Overdue (PR #73):** mobile's `groupTasksForList()` (`taskGrouping.ts`) mirrors web's `TIER_RANK` + `sort_order` ASC branching read-only for Today/Tomorrow/Day After Tomorrow/No Date — mobile has no drag-to-reorder UI and never writes `sort_order`, it only ever reflects whatever order was last set via the web app (or, for pre-PR-#61 tasks, the one-time `created_at` backfill) — but its Overdue section deliberately keeps the pre-PR-#73 2-way high/not-high split with `updated_at DESC` tiebreak (explicit in-code comment: "mirroring the backend's Overdue-vs-Today/Tomorrow distinction"), unlike web's Overdue column, which did adopt the full 3-way `TIER_RANK` in PR #73 — see PLAN-feat-priority-tiers.md. Reordering via the priority button (`handlePriorityStep`, PR #78 — renamed from `handleTogglePriority`; a 2-way up/down chevron stepper via `shiftPriorityTier()`/`resolveShiftedPriorityTier()` in `utils/taskPriority.ts`, replacing the single-button click-to-cycle `PRIORITY_CYCLE`/`resolveNextPriorityTier()` from PR #73) does **not** go through `handleDrop`/`computeInsertSortOrder` and sends no `sort_order` (only `priority`), so a task moved between tiers via the stepper (rather than dragged) keeps its prior `sort_order` value and can land anywhere within its new zone rather than at a predictable position — flagged in Doc's architectural review on PR #61, not addressed as of PR #73 or PR #78. **PR #78 also extends this same stepper button (previously All-view-only, via `TaskCard`) to Focused/Today/Tomorrow cards** (`FocusedTaskCard.tsx`'s own `handlePriorityStep`) — those cards call `updateTask` directly with no `handleDrop`/`sort_order` involvement at all (they were never draggable), so this "keeps its prior `sort_order`" caveat applies there too, unchanged from how a pre-PR #78 static badge view would have behaved had it been editable.

**Board order and order-driven default (PR #62, backend + web; mobile read-only):** `boards.sort_order` (`DOUBLE PRECISION NOT NULL`) mirrors `tasks.sort_order` (PR #61) exactly — a client-computed fractional index, reusing the same `_sort_order_default()` column default, backfilled per-user from `ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY is_default DESC, created_at ASC)` in the startup migration so no existing user's board order visibly changed on deploy. `GET /boards` and the three board-resolution queries in `focused_view_service.py` (`get_focused_tasks()`'s two branches, `get_day_view_tasks()`) all order by `Board.sort_order.asc(), Board.created_at.asc()` — replacing `is_default.desc(), created_at.asc()` for the boards list and `Board.name.asc()` for Focused/Today/Tomorrow/Overdue board grouping, so board display order is now identical and user-controlled everywhere it appears. `is_default` is no longer directly client-settable: `BoardUpdate.is_default` was removed from the schema (a client that still sends it gets a normal `200` with the field silently ignored, matching the `starter_questions` precedent from PR #50); instead, `board_service._recompute_default()` runs after every `sort_order` update and re-derives `is_default` from the full ordered board list — if the topmost board isn't already the default, it demotes the previous default and promotes the topmost board (same demote-then-promote flush order the old manual-set-default code used, avoiding the partial-unique-index `IntegrityError`). On web, `SettingsPage.tsx`'s `BoardEditor` gained native HTML5 drag-and-drop on each board row; `utils/boardOrder.ts`'s `computeBoardInsertSortOrder()` (same fractional-indexing algorithm as `utils/taskOrder.ts`) computes the drop position, sent via the new `reorderBoard()` (`BoardContext.tsx`, replacing the removed `setDefaultBoard`). The star/"set as default" button was replaced with a plain read-only marker on the topmost row. Mobile is deliberately read-only for order — it renders whatever order `GET /boards` returns (no local re-sort) but has no drag UI and never writes `sort_order`; its now-dead "Default" tap button was removed from `SettingsScreen.tsx` in the same PR. Board color also now drives styling beyond Settings' swatches (previously used only by `BoardGroupedTasks.tsx`'s board-header dot in Focused/Today/Tomorrow/Overdue and `FocusedTaskCard.tsx`'s left border): the extracted `utils/boardColor.ts` (`getBoardColor(color, index)` — a board's own color, or an 8-color `PALETTE` fallback by position) now also colors the All-view `BoardTabs.tsx` active-tab background/inactive-tab dot and `TaskCard.tsx`'s 4px left border (new required `boardColor` prop, computed once per page via `TasksPage.tsx`'s `activeBoardColor`), matching the treatment non-All views already had.

**Firebase Auth flow (Phase 2 frontend):** `AuthContext` mounts a single `onAuthStateChanged` listener. When `firebaseUser === null` and no deliberate sign-out is recorded in `sessionStorage` (`auth_signed_out`), it calls `signInAnonymously()` automatically — the user never sees a login screen. Deliberate sign-out sets `sessionStorage.auth_signed_out = '1'`, which prevents the auto-sign-in on the next listener fire; `LoginPage` is shown instead. Magic-link callbacks are handled on page load: if `localStorage.emailForSignIn` is present (same device), sign-in completes immediately; otherwise `EmailConfirmationPage` (an inline component in `App.tsx`) prompts the user for their email before completing the cross-device sign-in.

**Firebase Auth flow (mobile):** Mirrors the web pattern with React Native–specific adaptations. `AsyncStorage` replaces `localStorage`/`sessionStorage`. Auth persistence uses `getReactNativePersistence(AsyncStorage)` so the Firebase session survives app restarts. The deliberate-sign-out flag is a module-level variable (resets on force-quit — correct behaviour for a mobile app). Magic-link deep links are received via `expo-linking`: `Linking.getInitialURL()` handles cold-start links; `Linking.addEventListener('url', ...)` handles links while the app is open. Google Sign-In uses `expo-auth-session/providers/google` with separate web/iOS/Android client IDs from `EXPO_PUBLIC_GOOGLE_*_CLIENT_ID` env vars. In Expo Go, the Google OAuth redirect is `exp://[local-ip]:8081` and must be added to Google Cloud Console. Magic link deep linking only works fully in standalone builds; Expo Go cannot redirect back from the browser.

**Mobile form navigation (pageSheet Modal):** `TaskFormScreen` is not registered in the navigator; it is presented as a React Native `<Modal animationType="slide" presentationStyle="pageSheet">` owned by `TasksScreen`. This avoids a nested stack navigator and keeps the form decoupled — `TasksScreen` tracks `formVisible: boolean` and `editingTaskId: string | undefined` in local state. `onSave` and `onCancel` callbacks close the modal and trigger a silent re-fetch. When opening in create mode, `TasksScreen` passes `initialLabelIds={[...selectedLabelIds]}` to pre-select the currently active label filters in the form; in edit mode, `initialLabelIds` is `undefined` so the form always reflects the task's own labels. This pattern is the approved approach for full-screen forms in the mobile app.

**Mobile API error handling (ApiError):** `mobile/src/api/client.ts` exports an `ApiError` class (extends `Error`) with a readonly `status: number` property equal to the HTTP response status code. All `apiFetch` errors are thrown as `ApiError`. Callers use `instanceof ApiError` to branch on specific HTTP statuses (e.g. `err.status === 422` to catch the high-priority daily limit and display a user-friendly `Alert` without treating it as a generic failure). This pattern replaces the old practice of parsing error strings.

**Mobile drag-drop (TasksScreen):** Long-pressing a pending task for 500ms activates a `react-native-gesture-handler` Pan gesture via `GestureDetector`. A `TaskGhost` component floats at the finger position using `react-native-reanimated` shared values (`ghostY`, `ghostVisible`) updated in worklets to avoid JS-thread jank. The JS thread receives `runOnJS` callbacks (`onDragActivate`, `onDragMove`, `onDragEnd`) for target hit-testing and state updates. Section header Y positions are recorded via `onLayout`; hit-testing maps the finger's scroll-adjusted Y coordinate to the nearest section. On drop, only `target_date` is updated via `PUT /tasks/{id}` — matching web behaviour (`must_do_by` is never modified by drag). Dropping onto Overdue or Upcoming is rejected — `updateDragTarget` maps both to `null` (no highlight); `performDrop` returns early for both. The HP daily limit (fetched from `GET /settings` on every focus) is enforced client-side for today/tomorrow drops of already-HP tasks. Auto-scroll uses a 16ms `setInterval` that drives `getScrollResponder().scrollTo()` (an internal RN API used because `SectionList.scrollToLocation` does not support arbitrary Y offsets).

**Active board (mobile):** `BoardContext` tracks the user's currently selected board in React state. On mount, `BoardProvider` calls `GET /boards` and sets `activeBoard` to the default board (or the first board if no default exists). Active board is never persisted to `AsyncStorage` — every app open resets to the default board. `setActiveBoard` is called directly from the board switcher in `TasksScreen` (visible only in All view); no label clearing happens in `BoardContext` itself. Instead, each screen uses `useEffect([activeBoard?.id])` to react to board changes: `TasksScreen` clears label filters and search query (show-completed toggle removed in PR #46). All data-fetching calls in screens read `activeBoard?.id` and pass it as an optional `boardId` parameter. `useFocusEffect` in `TasksScreen` is guarded — it exits early if `activeBoard` is null (initial load). Every `BoardContext` mutation (create, rename, set-default, set-color, delete) awaits `fetchBoards()` to refresh the full boards list — no local-state patching. `setColorBoard(id, color)` calls `updateBoard(id, { color })` then `fetchBoards()` so the board list (and swatches in SettingsScreen) reflect the new color immediately.

**Shared task card body (mobile PR #46):** `TaskCardBody` is a shared component that was ported from web to mobile (React Native equivalent). It is consumed by both `TaskRow` (All view, `layout="inline"`) and `FocusedTaskCard` (Focused/Today/Tomorrow views, `layout="stacked"`) — extracted to close a parity gap where mobile's `FocusedTaskCard` had lacked Links/Complete/Delete buttons. It renders title, priority badge, dates, labels, links, and an Edit/Complete/Delete action row. Differences from web: both mobile call sites use `dateDisplay: {mode:'effective', effectiveDate}` (no `'split'` variant on mobile); and the action row gates Edit/Complete/Delete on `task.state === 'pending'` as inherited from TaskRow's pre-existing gate, which is inert in mobile's new UI since the "Show completed" toggle has been removed and only pending tasks are ever displayed (PR #46). **PR #74**: `TaskRow`'s `priorityBadge` changed from `'static'` to `'toggle'`, with a live `onTogglePriority` handler wired from `TasksScreen.tsx` (previously `'toggle'` mode existed in the component but no caller ever used it). `FocusedTaskCard` keeps `priorityBadge="static"` unchanged, per the locked-in Focused/Day View High-only decision.

**Mobile 4-way view system (PR #46):** `TasksScreen` reworked to replace the old 2-way Detailed/Focused toggle and "Show completed" toggle with a 4-way pill toggle (Focused, Today, Tomorrow, All) — default Focused. Focused renders `<FocusedView />` (GET /focused-view/tasks); Today/Tomorrow render `<DayView referenceDate={...} />` (GET /day-view/tasks for that single date); All renders the grouped-list SectionList with drag-drop, search, and label filters. Completing a task now removes it from view entirely — there is no remaining "Show completed" path in mobile's UI (unlike before). `DayView` (new component, PR #46) fetches GET /day-view/tasks for a caller-supplied `referenceDate` and delegates rendering to the shared `BoardGroupedTasks` component. Both `FocusedView` and `DayView` can be cross-board and show tasks from multiple boards grouped by board color.

**No shared module between web and mobile:** TypeScript types (`types/index.ts`) and pure utility functions (`taskDateUtils`, `taskFilters`, `taskPriority`, `taskLinks`, `dateRangePresets` — added PR #63) are duplicated from `frontend/src/` into `mobile/src/`. This is intentional — avoids monorepo complexity at the cost of keeping them in sync manually. `taskGrouping.ts` is mobile-only (no web equivalent) because the web app uses a kanban column layout rather than a grouped list. `isFormPriorityEligible` (renamed from `isFormHighPriorityEligible` — web in PR #73, mobile in PR #74) exists on both platforms, each deriving eligibility via its own `getColumn()` (PR #60, extended to mobile in a follow-up commit on the same PR): web's (`frontend/src/utils/taskPriority.ts`) covers overdue/today/tomorrow/day_after_tomorrow/Friday-only-monday; mobile's (`mobile/src/utils/taskPriority.ts`) covers overdue/today/tomorrow/day_after_tomorrow — mobile has no Monday case since its `ColumnKey` has no `'monday'` value (grouped list, not web's Friday-only Monday kanban column). Both previously used a narrower `<= tomorrow` date-string cutoff that PR #60 replaced on both platforms. `chatUtils.ts` was removed in PR #46 when the Chat feature was deleted from mobile.

**Task links:** A task may have up to `MAX_TASK_LINKS = 3` links, each `{id, url, description}`. `url` must start with `http://` or `https://` (rejects `javascript:`, `data:`, `mailto:`, etc. — both client-side via `isValidLinkUrl()` before submit and server-side via the `TaskLink` Pydantic `field_validator`); `description` must be non-empty after trim. `PUT /tasks/{id}` uses full-replace semantics for `links`, matching `label_ids`: omitting the field leaves existing links unchanged, any list (including `[]`) fully replaces the set. Both `TaskForm` (web) and `TaskFormScreen` (mobile) always send `links` on save so an empty array actually clears existing links. On the `/sync` push path, `SyncChanges.tasks` are raw dicts that bypass `TaskCreate`/`TaskUpdate` Pydantic validation entirely, so `sync.py`'s `_validate_sync_links()` re-validates each link independently via `TaskLink.model_validate()`; unlike the REST endpoints (where one invalid link fails the whole request with 422), an item-level failure during sync just drops that one link rather than discarding the whole array, and the result is capped at `MAX_TASK_LINKS`. Web renders read-only links (on task cards) as `<a target="_blank" rel="noopener noreferrer">` (native tooltip on hover shows the URL); mobile renders them as tappable chips that call `Linking.openURL()` after re-validating the scheme via `TaskCardBody.tsx`'s local `openTaskLink()` helper. `schemas.py` also defines an all-or-nothing `validate_task_links()` helper that is no longer called from application code (sync.py moved to per-item validation) — it is exercised only by `tests/unit/test_schemas.py`.

**Link editing UX in the form (PR #52, web + mobile):** `TaskForm`/`TaskFormScreen`'s links editor no longer has an explicit "+ Add link" button. A `useEffect` on the `links` state calls `withReadyLinkRow(links, newLinkId)` (`utils/taskLinks.ts`) after every change, which appends one blank row whenever the list doesn't already end in a single blank row and is under `MAX_TASK_LINKS` — so the user always has a ready-to-fill row without an extra step — and dedupes any extra blank rows down to the first (preserving its id) if a filled row is cleared back to blank. **Day View:** `GET /day-view/tasks?reference_date=YYYY-MM-DD&overdue=false` (`reference_date` required — no server-side default, unlike `GET /focused-view/tasks`; `overdue` optional, defaults to `false`, added PR #55) returns all pending tasks — any priority, across all boards — whose `must_do_by` or `target_date` falls on that single date (`overdue=false`, the default) or falls strictly before it (`overdue=true`), using the same OR-across-both-fields filter shape either way (`==` vs `<`). It ignores the user's Focused View config entirely (no `board_selection`/`day_range` concept). `focused_view_service._query_board_grouped_tasks()` is the shared query/grouping helper behind both `get_focused_tasks()` and `get_day_view_tasks()` — as of PR #55 it takes already-resolved, already-ordered `Board` objects and a caller-built SQLAlchemy `date_filter` clause (previously a fixed date window; each caller now builds its own `or_(...)` clause before calling in), and optionally filters to `Task.priority == "high"` (changed from `is_high_priority == True` in PR #72; the two columns stay mirrored on every write, so no behavior change — Medium is never distinguished from Normal by this filter). Tasks within each board group are sorted by `(Task.priority == "high")` DESC (high-priority first — same expression change, PR #72), then — as of PR #61 — `sort_order ASC` when `overdue=False` (Today/Tomorrow) or `updated_at DESC` (unchanged) when `overdue=True` (Overdue), via the helper's new `order_by_sort_order` param; prior to PR #61 both cases used `updated_at DESC`. Response reuses the existing `FocusedViewTasksOut` shape (each task carries both `priority` and the mirrored `is_high_priority`, PR #72). Added in PR #40 as backend groundwork for the web/mobile Today/Tomorrow views (later PRs in the same epic); extended in PR #55 to also back the Overdue view (see "Overdue view" above) — no new router or endpoint was added for Overdue.

**Move task between boards:** `TaskUpdate.board_id` (`Optional[str] = None`) lets a task move to a different board via `PUT /tasks/{id}` or `/sync` push. `task_service.update_task()` validates the destination board via `board_service.get_board_or_404()` (404 if not owned or soft-deleted) and unconditionally clears the task's labels when the board actually changes — regardless of whether the same request also sends `label_ids` — because labels are board-scoped and a label from the old board has no meaning on the new one. If `label_ids` is also sent in the same request, it is resolved against the *new* `board_id` (labels are re-added after the move). Omitting `board_id`, or sending the task's current `board_id`, is a no-op that leaves labels untouched. The `/sync` push path writes `server_task.board_id` directly from the client payload without calling `get_board_or_404()` — it does not validate that the destination board exists, is owned by the caller, or is not soft-deleted before assigning it. Added in PR #40.

**TaskForm mount stability across board switches (PR #48):** `TaskDetailPage` previously gated `<TaskForm>`'s render entirely on `pageLoading = loading || labelsLoading`. **Board pin (PR #69, web only):** Building on the collapse/expand mechanism above, `BoardCollapseContext` gained a second piece of session-only state, `pinned: Record<ViewKey, string | null>` (all `null` initially), with `isPinned(view, boardId)`, `pinBoard(view, boardId)`, `unpinBoard(view)`, and a raw accessor `getPinnedBoardId(view)`. `isCollapsed(view, boardId)` now delegates to a new pure helper, `effectiveCollapsed(pinnedBoardId, collapsedSet, boardId)` (`utils/boardVisibility.ts`, unit-tested in `__tests__/boardVisibility.test.ts`): when a board is pinned in a view, every other board reads as collapsed regardless of the underlying `collapsed[view]` Set, which is never mutated by pin/unpin — unpinning simply stops the override and whatever manual collapse layout existed pre-pin reappears untouched. `toggleBoard(view, boardId)` only clears an active pin on click (it does not also toggle the clicked board's membership in the Set on that same click — a deliberate unpin-first design, since combining unpin+toggle in one click is ambiguous when the pre-pin Set was empty); a second click then behaves as a normal toggle. `setAllCollapsed` also clears any active pin (an explicit, unambiguous bulk action). `BoardGroupedTasks` renders a new 📌 pin `<button>` per board header (`aria-pressed`, sibling to the existing collapse-toggle `<button>` — two siblings, not a nested button, since a `<button>` cannot contain another) and, in a `useEffect`, auto-unpins a view whenever its pinned board id is no longer present among that view's boards (board deleted, or its only qualifying task rescheduled out of the date window) — otherwise every remaining board would read as collapsed with no per-board affordance to recover, short of the manual "Expand all" escape hatch (caught by Sneezy's plan review before implementation). **Tag filter modes and per-board persistence (PR #70, #71, #75, web only):** `taskFilters.ts`'s `filterTasks()` takes a `matchMode` as an optional 4th argument — introduced as `'AND' | 'OR'` in PR #70 (`'AND'` requires every selected label on the task, `'OR'` requires any), widened to the shared `FilterMode = 'SINGLE' | 'AND' | 'OR'` type in PR #75 (default changed from `'AND'` to `'SINGLE'`). Through PR #70/#71, both `TasksPage.tsx` (All view) and `BoardGroupedTasks.tsx` (Overdue/Focused/Today/Tomorrow, via its single visible board) held selected-label-ids and match-mode as **separate** state — a global `FilterContext` Set for the former, local `useState` for the latter — with `BoardContext.setActiveBoard` clearing `FilterContext`'s selection on every board-tab switch, and `BoardGroupedTasks` resetting its own local selection/mode on every qualifying-board change. **PR #75 replaces both mechanisms with one shared, board-keyed store in `FilterContext`:** `boardLabelSelections: Map<string, Set<string>>`, exposed as `getBoardLabelSelection(boardId)`/`toggleBoardLabel(boardId, labelId)`/`clearBoardLabelSelection(boardId)`, plus a single shared `matchMode`/`setMatchMode`. Both `TasksPage.tsx` (keyed on `activeBoard.id`) and `BoardGroupedTasks.tsx` (keyed on `singleVisibleBoard?.board_id`) now read/write the *same* per-board entries through this one context — a board's selected tags look identical whether last viewed via an All-view tab or a pinned/single-board view — and `BoardContext.setActiveBoard` no longer clears anything on switch, since each board's selection now lives in its own map entry rather than one shared Set. Toggling within a board (`toggleBoardLabel`) routes through the new shared `toggleLabelSelection(prev, id, mode)` helper (`utils/taskFilters.ts`): in `SINGLE` mode, clicking a tag replaces the board's whole selection with just that tag (clicking the already-selected tag deselects it); `AND`/`OR` keep the pre-existing toggle-in-set behavior. The "Single mode ⇒ at most one tag selected" invariant is enforced **locally, per view, only for the board actually on screen** — `TasksPage.tsx` and `BoardGroupedTasks.tsx` each run their own `useEffect` keyed on `` `${boardId}:${matchMode}` `` that clears that view's currently-visible board's selection when it holds more than one tag under `SINGLE` mode. This is a deliberate, not-a-global-sweep design: an earlier draft had `setMatchMode` itself sweep every board's `size > 1` entry on switch-to-Single, which was rejected mid-plan-review because it would silently mutate a different, off-screen board's remembered selection the instant the mode changed anywhere in the app — directly undercutting the whole point of per-board persistence. The tradeoff: a board with a stale multi-tag selection that nobody has viewed since switching to Single keeps showing that selection until it's next viewed, reconciling (clearing) at that moment rather than pre-emptively (see PLAN-feat-tag-filter-single-mode.md). `LabelFilterChips` (`frontend/src/components/LabelFilterChips.tsx`) renders the `Single | AND | OR` 3-button mode pill and "Clear filters" **unconditionally** as of PR #75 (previously gated on selection size) — Clear is `disabled` rather than unmounted when nothing is selected — laid out as of PR #75 as two `justify-between` flex groups (chips left, mode+Clear right). **PR #79** swaps the two groups' sides and drops wrapping in favor of horizontal scroll: mode pill + "Clear filters" now render first (left), the tag-pill group renders second and right-aligns (hugs the right edge, `overflow-x-auto` scroll on overflow instead of wrapping to a second line — mirrors `BoardTabs.tsx`'s pill-scrolling pattern). See `components/LabelFilterChips.tsx` above for the exact class changes.

**Overdue view (PR #55, web + mobile):** A fifth, conditionally-rendered top-level Tasks-page view — Overdue — sits to the left of Focused in the pill toggle, shown only when the caller has at least one overdue task, and becomes the default view (instead of Focused) on page load/first tab focus when overdue tasks exist. "Overdue" = a pending task whose effective date (earliest of `must_do_by`/`target_date` when both are set, otherwise whichever is non-null) is strictly before today — the same definition already used by the All view's kanban Overdue column, but this is a distinct, separate view (the kanban column is unaffected and unrelated). **Archive board filtering and date-range presets (PR #63, web + mobile):** Reports was renamed to Archive throughout (nav label, page/screen component, web route `/archive` with a `/reports` → `/archive` redirect for old links; the backend `/reports/completions` endpoint path itself is unchanged — only the UI-facing name changed). When `all_boards=true`, the backend (`reports_service.get_completions()`) returns an additive `boards: List[BoardCompletions]` field (board-ordered per the user's custom `sort_order`, boards with zero matching completions omitted) alongside the pre-existing flat `completions` list; the frontend renders `<ArchiveBoardGroups>` (Today-view-style board-grouped, collapsible cards) when `boards` is present, falling back to the pre-existing flat-list rendering when a single board tab is selected (`boards` is `null`/absent in that response shape). Fully backward-compatible: `board_id`-only callers (including not-yet-updated future clients) get the exact pre-PR #63 response shape.

**Search across all views (PR #56, web only):** The task search box (title + notes, client-side substring match) previously filtered only the All view's kanban board. `TasksPage` now passes `searchQuery` down into all five views: `filterTasks` (All view, unchanged behavior, now built on the shared `matchesSearch` predicate in `utils/taskFilters.ts`) and the new `filterBoards(boards, searchQuery)` (Overdue/Focused/Today/Tomorrow, applied inside `BoardGroupedTasks`). `filterBoards` filters each board's task list independently and drops boards left with zero matches; when the raw board list was non-empty but the filtered result is empty, `BoardGroupedTasks` renders a "No tasks match this search" empty state in place of its normal output, suppressing the "Collapse all"/"Expand all" toggle so it never points at nothing. This is a web-only change — mobile's `TasksScreen` search remains scoped to the All view's filter panel, unchanged by this PR. (Search box positioning was subsequently moved by PR #57 — see below.)

**All-view UX polish (PR #57, web only):** Nine small polish items on the web Tasks page, all frontend-only (no backend/API/data-model changes). (1) Sticky high-priority collapse: the All view's per-column high-priority-zone collapse state moved out of `TasksPage`'s local `useState` into a new `ColumnPriorityCollapseContext` (mirroring `BoardCollapseContext`'s already-established "mount above `BrowserRouter`" pattern, keyed only by `ColumnKey` since it's All-view-only) — collapse state now survives navigating to a task's edit page and back. (2) Each priority-eligible column's "High Priority" zone header shows a live count, "High Priority (n)". (3)/(4) The filter-chip row's redundant "Tags" label (`CATEGORY_DISPLAY_NAMES`) was removed and "Clear filters" is right-aligned under the chips. (5) The search `<input>` (introduced All-view-only, extended to all views in PR #56) now renders as the topmost element on the page, above the title/view-toggle Header block and unconditionally (not gated on the `overdueChecked` first-paint check) — a bigger reorder than "move to the top" might suggest at a glance, since it now sits above "Tasks Are Us - `{view}`" itself, not just above `BoardTabs`. (6) `TaskCard`'s label container always renders (no longer `null` for zero-label tasks) with a `min-h-[2.75rem]` (2 chip rows) floor, so switching boards no longer changes card/column height depending on how many labels each board's tasks carry; `FocusedTaskCard`'s equivalent pattern in Focused/Today/Tomorrow was intentionally left out of scope, flagged as a known follow-up. (7)/(8) `taskDateUtils.formatDateWithDay()` switched from full to abbreviated weekday names (`'long'` → `'short'`), and `TasksPage`'s `COLUMNS` memo now carries `{ title, dateLabel? }` per entry instead of one pre-concatenated title string, so column headers render the date label on its own line below the column name. (9) `TaskQuickEdit`'s label buttons are now alphabetized by `label.value`, matching the sort already used by the filter-chip row.

**Markdown Notes preview (PR #59, web + mobile):** The Add/Edit Task form's Notes field gained a live-updating, read-only Markdown preview on both platforms — UI-only, no backend/data-model/API changes; `notes` is still stored and submitted as trimmed plain text (Markdown is a purely client-side rendering interpretation of that same string). **Web** (`TaskForm.tsx`): a responsive `grid grid-cols-1 md:grid-cols-2` splits the existing textarea (left) from a new scroll-capped (`max-h-80`) preview pane (right) rendered via `react-markdown` + `remark-gfm` (new dependencies), styled with `@tailwindcss/typography`'s `prose prose-sm` classes (new dev dependency, registered in `tailwind.config.js`). Rendered links get `target="_blank" rel="noopener noreferrer"` so a click can't navigate the SPA away from an in-progress unsaved form; GFM task-list checkboxes are forced `disabled` (inert). No HTML-sanitization step is needed — `react-markdown` renders to React elements (never `dangerouslySetInnerHTML`) and its default `urlTransform` already blocks non-allowlisted URL schemes (`javascript:`, `data:`, etc.) on links/images. **PR #80** (web only): the textarea and preview pane scroll in sync in both directions, proportional by scroll percentage — see the `TaskForm.tsx` entry in Code Structure above for the mechanism and an open testability/correctness note from Doc's review. **Mobile** (`TaskFormScreen.tsx`): a stacked (not side-by-side) preview `<View>` below the existing `<TextInput>`, capped `maxHeight: 200` with a nested `ScrollView`, using `<Markdown>` from `@believer/react-native-markdown-display` (new dependency) with a custom `markdown-it` instance (`markdown-it-task-lists`, new dependency, typed via a local `.d.ts` shim) for GFM checklist parity with web, a custom `rules.html_inline` override to actually render the plugin's raw-HTML checkbox tokens as ☑/☐ glyphs (this renderer family has no built-in rule for them), and an explicit node-type `style` map (NativeWind `className` doesn't reach this library's internal render tree, same limitation as mobile label badge colors below). Links tap through the existing `openTaskLink` helper via `onLinkPress` (returning `false` to suppress the library's own default open behavior), not a second implementation. **Known gap (flagged in Doc's architectural review on this PR):** the mobile markdown package actually installed (`@believer/react-native-markdown-display`) was chosen at implementation time and was not evaluated by name in either of the plan's two review passes (which assessed `react-native-markdown-display` and a different named fork); the on-device/simulator smoke test under Expo SDK 54 + New Architecture (`newArchEnabled: true`) that the plan and both reviews required before shipping had not been run as of this PR (no simulator available in the implementation environment) — an open item that must be resolved before the mobile bundle ships via `eas update`.

The frontend build requires these to initialise Firebase Auth — anonymous sign-in on first load will fail silently without them. In production (Railway), set these as frontend service env vars.

Copy `mobile/.env.example` → `mobile/.env`; set all `EXPO_PUBLIC_FIREBASE_*` env vars and `EXPO_PUBLIC_GOOGLE_*_CLIENT_ID` env vars. Set `EXPO_PUBLIC_API_URL` to your machine's local IP (e.g. `http://192.168.1.100:8000`) — `localhost` does not resolve from a physical device or emulator to the host machine. For Google Sign-In in Expo Go, add the `exp://[local-ip]:8081` redirect URI to Google Cloud Console → Authorized redirect URIs.
